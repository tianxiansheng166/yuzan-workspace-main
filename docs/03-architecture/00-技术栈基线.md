# 技术栈基线

版本是工作区生成时的建议基线，GOV-001 必须在实际开发机重新验证兼容性并生成 lockfile。

| 层              | 建议                                                        |
| --------------- | ----------------------------------------------------------- |
| Runtime         | Node.js 24 LTS（兼容性优先，不追逐最新 Current）            |
| Package manager | pnpm workspace                                              |
| Web             | Nuxt 4 + Vue 3 + TypeScript                                 |
| API             | NestJS 11 + TypeScript                                      |
| Database        | PostgreSQL 17                                               |
| ORM/migrations  | Prisma 7                                                    |
| Object storage  | S3-compatible（开发 MinIO）                                 |
| Worker          | 独立 Node 进程；队列按需求引入                              |
| Contracts       | OpenAPI 3.1 + 生成 TypeScript                               |
| Web tests       | Vitest + Playwright（Wave 0/QA 安装）                       |
| API tests       | Vitest + PostgreSQL integration                             |
| Offline         | PWA + IndexedDB + outbox                                    |
| Observability   | structured logs + health + metrics                          |
| Deployment      | Docker Compose 开发；staging/production 方案由 OPS-001 决定 |

## 为什么不直接采用 Element Plus 作为 UI

可以使用成熟无头组件解决复杂可访问行为，但视觉系统必须由 `packages/ui` 的 token 和项目组件控制。通用后台组件库若直接决定页面外观，会重新产生卡片墙、同质化表单和“学生项目后台”感。

## 为什么不立即微服务

首期数据一致性、租户权限和研发速度比独立扩展更重要。模块化单体保留清晰边界，未来只有在真实负载、团队或故障隔离证据出现时才拆分。

## 为什么不长期双写旧 JSON

双写会引入两个事实源、失败补偿和不可验证的一致性。旧 JSON 只作为一次性迁移输入，新 PostgreSQL 是唯一运行时事实源。
