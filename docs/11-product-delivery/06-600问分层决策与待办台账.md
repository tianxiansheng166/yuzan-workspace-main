# 06｜600 问分层决策与待办台账

## 使用结论

这份 600 问 HTML 是一套很有价值的风险题库，但它不是 PRD、架构或开发计划。它目前把回答保存在浏览器 LocalStorage 中，缺少负责人、批准人、证据、版本和依赖，因此不能成为团队唯一事实源。

正确用法不是“先把 600 题都写满再开发”，而是：

1. 按决策时域分层；
2. 只关闭会阻塞当前门禁的问题；
3. 每个答案记录状态、负责人、批准人、证据和日期；
4. 已确认答案进入 PRD/架构/试点方案，题库只保留索引；
5. 事实变化时新建 revision，不覆盖历史决定。

## 决策时域

| 时域 | 必须关闭时间 | 典型问题 | 未关闭的后果 |
| --- | --- | --- | --- |
| A 比赛闭环 | 立即，进入波次 1 前 | 产品定义、唯一 P0、端形态、Attempt、评分边界、验收 | 禁止继续扩功能 |
| B 可用 MVP | 真实用户测试前 | 身份权限、状态、弱网、失败恢复、动态数据 | 禁止称为可用产品 |
| C 首校试点 | 学生真实数据进入前 | 学校、人数、课表、授权、实施、SLA、停止条件 | `NO-GO` |
| D 商业复制 | 报价/融资尽调前 | 付费方、合同、成本、续费、扩校 | 只能陈述假设，不能陈述成果 |
| E 已移出/不适用 | 每次范围复核 | App、社区、志愿者、大屏等 | 保持冻结，不进入当前任务 |

## 个性化默认决策

以下答案基于当前项目、源码和比赛约束，可以作为讨论默认值；带“待批准”的仍不是既成事实。

| 决策 | 默认值 |
| --- | --- |
| 产品核心 | 学习证据与教师干预闭环 |
| 第一价值对象 | 教师和学生共同构成的教学闭环，不单独优化某一端 |
| 使用组织 | 教师强组织，学生完成被投递任务；暂不以自主学习为主 |
| 学生端 | 微信小程序目标形态；移动 H5 作为时间不足时的诚实过渡 |
| 教师端 | 桌面 Web |
| 管理端 | 桌面 Web 最小治理 |
| 部署形态 | 当前为共享服务的逻辑租户隔离；真实学校策略待安全评审 |
| 内容范围 | 一个古诗文内容单元；课程、练习和规则版本化 |
| 自动评分 | 辅助处理，不自动替代教师最终判断 |
| AI 教案/翻译 | P1 草稿工具，服务端 adapter + schema 校验 + 人审 |
| 重做 | 新 Attempt，不覆盖旧 Attempt |
| 报告 | 来源、状态、revision 可追溯；待复核时不显示假分数 |
| App/社区/志愿者/大屏 | P2 冻结 |
| 公共门户 | P1 最小可信介绍与试点入口，不是核心产品 |
| 演示数据 | 专用 demo tenant，可重置但走真实 API，不用本地假 token |
| 商业数字 | 无证据前一律称假设，不沿用旧文档的价格或效果数字 |

## 决策记录模板

不要只在群聊中回复“好的”。每个关闭问题使用：

```yaml
decision_id: DEC-...
question_ids: [1, 2]
status: PROPOSED | APPROVED | SUPERSEDED
decision: 一句话、无歧义的决定
rationale: 为什么这样选
owner: 负责推动的人
approver: 有最终裁决权的人
evidence: 访谈、合同、源码、测试或法规依据
effective_date: YYYY-MM-DD
affects: PRD、对象、接口、页面、试点或商业材料
revisit_trigger: 什么事实发生时必须重审
```

## 维护方式

- HTML 继续作为便于浏览和筛选的题库；
- 团队协作答案迁移到版本控制中的决策记录或正式协作表，不再只放 LocalStorage；
- 每道题只引用最终决策，不在多个文档复制一段不同答案；
- 每周决策会最多处理 5—10 个当前门禁问题；
- 未影响当前门禁的问题保持 `DEFERRED`，不消耗开发周期；
- 任何被真实证据推翻的答案标记 `SUPERSEDED`，保留历史和原因。
