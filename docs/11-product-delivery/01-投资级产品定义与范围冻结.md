# 01｜投资级产品定义与范围冻结

## 当前结论

专业人士指出的问题基本成立：原文档不是一份可直接施工的标准 PRD，而是战略、商业、试点、远期蓝图和工程审计的混合体；现有开发也存在“页面和模块很多，但真实业务闭环证据不足”的结构性风险。

但这不等于项目毫无价值或必须推倒重来。真正的问题不是“一个人不能写全栈”，而是当前缺少一套能让任何团队成员回答以下问题的共同系统：

1. 当前版本唯一要闭合的用户结果是什么；
2. 哪些事实已经被源码和运行证据证明；
3. 哪些只是设计、部分实现或演示兜底；
4. 每个对象由谁创建、何时变更、失败后如何恢复；
5. 下一个任务依赖什么、如何验收、失败时回退什么；
6. 面对评审、学校和投资人时，哪些话能说，哪些不能说。

所以现在的正确动作不是继续堆页面，也不是先把 600 个问题逐篇长答，而是完成“范围冻结 → 真实闭环 → 可信演示 → 首校门禁 → 商业验证”五级收敛。

## 产品一句话定义

语赞心声是一套面向民族地区语文学习场景的教学服务平台：教师投递结构化学习任务，学生通过移动端产生朗读和理解证据，系统辅助处理，教师完成复核与干预，学校获得可审计的学习过程与异常信息。

这里的核心不是“AI 能自动打多少分”，而是建立一条低成本、可追溯、有人负责最终判断的学习证据闭环。

## 谁使用、谁受益、谁付费

| 角色 | 核心任务 | 获得价值 | 当前必须验证的假设 |
| --- | --- | --- | --- |
| 学生 | 看任务、练习、录音、查看报告、复测 | 知道哪里错、下一步练什么 | 手机和网络条件允许；反馈可理解；愿意复测 |
| 教师 | 投递、看进度、复核、反馈、干预 | 降低重复劳动并保留专业判断 | 复核队列真的节省时间，而非增加负担 |
| 学校管理员 | 管组织、账号、授权、使用情况 | 可控部署、可审计使用、看见异常 | 学校愿意承担实施与合规责任 |
| 教研/内容人员 | 维护课程和练习版本 | 内容可复用、可追踪、可迭代 | 能形成稳定的最小内容生产流程 |
| 采购/资助方 | 采购或资助试点 | 可验证的教育服务结果 | 价值主张和采购路径真实存在 |

“投资人”不是产品用户。投资人判断的是团队能否用有限资源把上述价值和商业假设逐级证明。

## 唯一 P0

首个冻结版本只做一个内容单元、一个班级上下文、两类核心身份和一条黄金闭环：

```text
教师 Web 发布练习
  → 学生移动端收到任务
  → 学生完成录音与理解题
  → 服务端保存 Attempt、Answer、Recording 并触发处理
  → 低置信度或规则命中的结果进入教师复核
  → 教师基于真实证据确认、修改或要求重做
  → 系统生成可解释报告并投递巩固
  → 学生查看报告并完成复测
```

比赛现场的专业感来自评审扫码后能走通真实流程，并能在教师端看到刚刚产生的记录，而不是来自页面数量。

## 产品形态冻结

| 端 | 本阶段定位 | 原因 |
| --- | --- | --- |
| 学生小程序 | P0 目标端；优先实现 6—8 个核心页面 | 进入成本低，符合扫码演示和日常触达场景 |
| 教师 Web | P0 | 复杂表格、批量操作、音频证据和复核更适合桌面端 |
| 学校管理 Web | P0 最小能力 | 组织、账号、授权与审计不能藏在研发脚本里 |
| 公共门户 | P1，仅保留可信介绍和试点入口 | 没有服务闭环的展示站商业价值有限 |
| 原生 App | P2，当前冻结 | 增加研发、审核和维护成本，尚无独占能力证明 |
| 内容运营后台 | P1，先用最小受控流程 | 先证明内容单元和版本机制，再建设完整后台 |

小程序和 Web 共用业务 API、对象与权限规则，但不应假设“响应式网页一键打包”就等于完成小程序。录音权限、文件上传、登录态、分包、隐私声明、合法域名和真机兼容都需要独立验收。

## 本版本范围

### P0 必做

- 真实登录与学校/班级/角色上下文，不允许 API 失败后生成假 token；
- 教师创建并发布练习，学生只看到自己有权访问的任务；
- 学生提交文字答案和真实音频，上传、重试、超时、取消均有明确状态；
- 动态提交 ID 贯穿教师复核，不允许固定 `submission-1`；
- 机器结果与教师结果分别保存，教师修改必须可追溯；
- 报告来源真实，不能用固定分数、固定指标或伪造用户数据；
- 要求重做时保留原提交，只新增复测或新尝试；
- 最小学校账号、班级和授权管理；
- 手机真机和桌面浏览器各完成一次黄金闭环；
- 运行脚本可重复启动、识别已有服务，并能说明服务所有权。

### P1 在 P0 通过后再做

- 内容运营工作台；
- AI 教案草稿和双语翻译的人审工作流；
- 教师批量投递、班级趋势和更细的报告；
- 首校实施配置、培训、帮助和反馈入口；
- 公共门户的试点申请与可信案例展示。

### 当前不进入范围

- 原生 App；
- 志愿者和一对一帮扶；
- 文化社区和内容社交；
- 区域治理大屏；
- 自动替代教师的最终评价；
- 未经教研和真实数据验证的复杂个性化推荐；
- 同时覆盖多个年级、多学科和多种地区语言；
- 把比赛演示数据包装成真实商业或教学效果。

## 三个时域必须分开

| 时域 | 目标 | 允许的证明 | 禁止混淆 |
| --- | --- | --- | --- |
| 比赛 Demo | 5—8 分钟稳定呈现真实核心价值 | 受控演示环境、一个内容单元、少量测试账号 | 不能说已经大规模商用 |
| 首校 MVP | 连续数周服务一个真实班级 | 真实授权、实施记录、使用数据、问题闭环 | 不能拿一次演示代替试点效果 |
| 商业产品 | 可复制交付、采购、续费和扩校 | 合同/意向、单位经济、SLA、合规和多校运维 | 不能把远期蓝图算作现有能力 |

## 投资叙事

当前最可信的叙事是：团队已经形成一批可复用的学习、作业、录音、异步处理和报告工程资产，下一阶段用一个高频、可测量的教学闭环证明产品价值，再通过首校验证复核效率、完成率和实施成本。

当前不应声称：

- 已形成完整的全栈商业平台；
- 已达到学校可采购或规模化交付；
- AI 评分已经替代教师；
- 已验证教学效果、付费意愿或单位经济；
- 现有网页可以无成本变成生产级小程序。

## 成功指标

### 比赛版本

- 真实跨角色黄金闭环连续演示 3 次成功；
- 任意一次提交均可由动态 ID 在教师端追溯；
- 演示流程不存在假 token、固定业务 ID、固定指标和静默降级；
- 手机核心页面无文字重叠、横向溢出或不可点击控件；
- 关键供应商不可用时页面明确降级，不伪造结果。

### 首校版本

- 指标口径在试点前冻结：任务到达率、有效提交率、教师复核耗时、重做完成率、异常率；
- 所有指标能回溯到业务事件和对象，而不是人工拼报表；
- 权限、隐私、数据保留、删除和事故响应通过门禁；
- 教师愿意持续使用且复核负担在约定范围内；
- 学校能完成组织、账号、设备和网络实施。

## 待项目方决策

以下问题会改变产品或开发路径，不能由研发擅自编造：

1. 产品负责人、业务验收人、教研负责人和技术负责人分别是谁；
2. 比赛日期、现场网络、演示时长和评审最关注的评分项是什么；
3. 首个内容单元具体是哪一课，朗读、理解和巩固题各多少；
4. 首校是否已有明确对象；年级、班级、人数、设备和周期是什么；
5. 谁拥有内容版权和学生录音处理授权；
6. 教师复核触发规则、目标工时与 SLA 是什么；
7. 首校成功后由谁付费、按什么单位付费、谁签署采购；
8. 语音评分采用哪一条可上线的供应商/开源路线，准确性如何验收；
9. 藏汉翻译是否属于首校必需能力，谁负责最终人审；
10. 未成年人和民族语言数据的保存位置、期限、删除责任和授权文本由谁批准。

这些决策的完整分级和关闭顺序见[600 问分层决策与待办台账](./06-600问分层决策与待办台账.md)。
