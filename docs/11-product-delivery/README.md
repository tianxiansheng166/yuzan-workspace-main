## 当前结论

语赞心声不应继续被定义为“一个教育网页”，也不能靠把现有网页自适应后直接打包成小程序来证明产品成立。当前最合理的产品形态是：

- 学生侧：微信小程序优先，承载今日任务、练习、录音、报告和巩固复测；
- 教师侧：Web 工作台，承载投递、进度、复核、反馈和干预；
- 学校侧：Web 管理后台，承载组织、账号、授权、使用概览和审计；
- 服务侧：统一业务 API、数据、文件、异步任务和供应商适配层；
- 公共门户：只承担可信介绍和试点转化，不承担核心学习闭环。

这不是从零重构。当前仓库已经有课程、练习、作业、提交、录音、语音任务、报告、AI 教案和翻译等模型与接口资产。接下来要做的是停止横向铺功能，先消除演示伪路径，打通一条真实、可重复、可审计的 P0 黄金闭环。

## 唯一 P0

> 教师发布一份古诗文朗读与理解练习 → 学生在移动端完成真实录音与作答 → 服务端保存证据并处理 → 教师查看动态提交、复核并投递巩固 → 学生查看真实报告并完成复测。

任何不能直接支撑这条闭环的功能，在闭环验收前不得争夺 P0 开发资源。

- 团队负责人先审阅 01、06、07，冻结负责人、首个内容单元、首校假设和比赛目标；
- 产品、设计、研发共同审阅 02、03、04，所有争议落到对象、状态、权限或验收标准；
- 开发只从 05 中领取满足前置依赖的任务包；
- 每次迭代必须提交源码检查、真实 API、浏览器流程、数据库结果和异常路径证据；
- 旧《投资与产品版 Strategic PRD》保留为上游战略母文档，不再直接用作研发施工单；
- 旧 P0 黄金闭环、页面地图和产品决策记录继续作为专项参考，但如与当前源码或本包门禁冲突，以“真实运行证据 + 本包已冻结决策”为准并补充决策记录。

## 当前状态标签

本文档统一使用以下标签，避免把“写过代码”误报成“产品可用”：

| 标签 | 含义 |
| --- | --- |
| `SOURCE_PRESENT` | 源码或模型存在，尚未证明运行有效 |
| `BUILD_PASS` | 构建或测试通过，尚未证明真实用户流程 |
| `RUNTIME_REACHABLE` | 端点或页面可访问，尚未证明业务闭环 |
| `FLOW_VERIFIED` | 真实身份、动态数据、浏览器、API 和数据库证据完整 |
| `PILOT_READY` | 除闭环外，组织、权限、隐私、运维和实施门禁也通过 |
| `BLOCKED` | 关键依赖或事实未满足，禁止对外宣称完成 |

截至本基线，项目属于 `BUILD_PASS + 部分 RUNTIME_REACHABLE`，不是 `FLOW_VERIFIED`，更不是 `PILOT_READY`。

## 文档维护规则

- 任何“已完成”必须附提交 SHA、环境、测试命令和证据路径；
- 任何涉及真实学校、人数、预算、效果、合同和供应商可用性的说法，在获得书面证据前均标记为“待确认”；
- 业务对象、状态或 API 契约变更必须同步更新 PRD、OpenAPI、数据库模型和调用方；
- 600 问不是一次性作文任务，只关闭会影响当前门禁的问题；
- 每两周做一次产品复核：删除无证据主张、关闭已决问题、重新排序下一波任务。
