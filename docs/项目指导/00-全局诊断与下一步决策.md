# 全局诊断与下一步决策

> 诊断范围：`apps/api`、`apps/worker`、`web-runtime`  
> 明确排除：`apps/apps-web`  
> 诊断日期：2026-07-19

## 一、先说结论

这次与 AI 的对话，产品方向判断大约有八成是对的：它终于把项目从“学生端、教师端、管理端分别堆页面”拉回到了同一个产品内核——课程、练习、语音证据、评分、报告、能力画像和教学干预。

其中最有价值的三个判断是：

1. **一套练习引擎，多种交付模式。** 自主练习、课程练习、教师作业、班级测评不应该各做一套执行流程。
2. **真正的闭环是证据闭环。** 学完内容后必须产生录音或作答证据，证据进入评分、复核、报告和下一步推荐。
3. **先跑通一条黄金闭环。** “古诗文朗读与理解训练”比继续铺几十个页面更能验证产品价值。

但对话中的方案还不能原样变成开发任务。它需要五处修正：

1. 不应立刻重建八个新模块。当前仓库已有 `curriculum`、`learning`、`assignments`、`submissions`、`assessment`、`recordings`、`speech-job`、`reporting`，应先做领域映射和最小增量。
2. “对标广东英语听说系统”应理解为对标设备检查、题型执行、计时、录音、评分、复核和报告能力，不能照搬题型、内容、评分口径或界面。
3. AI 备课、AI 练习生成和推荐不是第一阶段前提。没有稳定内容模型、能力标签、评分标准和真实数据时，AI 只会放大混乱。
4. “数据护城河”必须建立在未成年人隐私、授权、最小化采集、用途限制、保留期限和人工复核之上，不能只强调积累数据。
5. 现在首先需要修复的是契约、测试和真实内容交付，不是先替换框架，也不是再重做一轮视觉。

## 二、当前项目的真实状态

### 1. 后端 `apps/api`

当前后端不是空壳，已经具备较完整的 NestJS 模块化单体基础：

- 登录、会话、选校和学校范围；
- 课程版本、班级、作业、学习进度、提交和反馈；
- 新增的测评会话、测评题目、书面答案、报告和复测；
- 录音初始化、上传地址、完成和证据读取；
- SpeechJob 创建、查询和结果回写；
- 学生聚合页、教师聚合页和教师工具草稿；
- PostgreSQL + Prisma 的真实模型；
- 请求 ID、异常过滤、输入校验、角色和租户保护。

这说明方向讨论里“重新建立完整后端”的表达过重。真正缺的是把现有模块收敛成统一练习领域，并让契约、测试和前端同步。

### 2. worker `apps/worker`

worker 当前主要承担语音评分队列：

```text
BullMQ 取任务
→ 从对象存储获取录音下载地址
→ 调用 Python 语音评分服务
→ 回写 SpeechJob
→ 回写 AssessmentItem
→ 更新 Recording 状态
```

这个链路的结构是合理的，但成熟度还不够：

- `reporting/` 和 `media/` 仍为空目录；
- 默认可关闭语音供应商；
- 没有 worker 测试文件；
- 失败重试、幂等、重复回调、坏音频、超时和租户负向场景缺少自动化证据；
- 评分输出只有固定的 reading score 结构，尚未支持按题型、评分量表版本和学校策略解释结果。

### 3. 前端 `web-runtime`

`web-runtime` 是当前真实前端，但它不是 Nuxt/Vue 应用。它是：

```text
多页 HTML/CSS/JavaScript
+ Node 静态服务器
+ /api/v1 反向代理
+ localStorage/IndexedDB
```

它的优点是启动快、便于赶工和视觉验收；当前已经有统一 API 客户端、登录/选校、部分真实教学链路和新的动态测评 shell。

它的问题也很明确：

- 页面技术形态不统一，既有手写多页，也有打包后的 React 页面；
- 许多页面仍把业务数据写在 HTML 或 JavaScript 常量中；
- 路由中仍有 `spring-2`、`submission-1` 等演示标识；
- 教师首页、教师测评任务列表和测评详情的大量数据仍是静态数据；
- 状态文档与当前代码已经不一致；
- 缺少统一的前端自动化测试和真实纵向 E2E；
- API 失败时部分页面会静默回退或继续展示默认内容，容易形成“看起来成功”。

赶工阶段不建议马上迁移框架。先用 `web-runtime` 跑通黄金闭环；等业务对象和接口稳定后，再决定是否迁移到 Nuxt。

## 三、已经确认的关键断点

### 断点 1：OpenAPI 已落后于实现

当前 OpenAPI 只有约 28 条路径，没有覆盖已经出现的测评会话、录音、SpeechJob、教师聚合和教师工具等核心接口。现在形成了三套事实：

```text
后端 Controller
前端 api-client.js
OpenAPI
```

三者不一致时，后续 AI 会继续各自猜接口。赶工第一天必须重新冻结契约。

### 断点 2：教师发布测评可能直接失败或产生空测评

教师创建页调用 `createClassAssessment` 时省略了 `enrollmentIds` 和 `questionIds`：

- 后端 DTO 当前把 `enrollmentIds` 设为必填数组；
- service 虽然支持“不传学生时取全班学生”，但请求会先被 DTO 校验拦截；
- service 明确说明当前无法从班级自动解析默认题目，调用者必须传 `questionIds`；
- 即使绕过 DTO，未传题目也会给每名学生创建没有 `AssessmentItem` 的空 session。

这是当前最优先修复的真实前后端契约问题。

### 断点 3：有测评会话，但没有可复用的练习定义

现有 `AssessmentSession`、`AssessmentItem` 更像“一次执行”，不是可发布、可版本化、可复用的练习或试卷。当前缺少：

- 练习定义与版本；
- section 顺序和执行规则；
- 题型配置；
- 示范音频与是否显示文本；
- 播放、准备、录音、重录次数；
- 评分量表版本；
- 交付模式和截止规则；
- 自主练习可见性；
- 内容版权与来源状态。

因此对话里“测评像一次性的”这个诊断完全成立。

### 断点 4：报告只是简单平均

当前报告生成逻辑主要把已评分题目的 `scoredScore` 做平均：

- 没有按 `maxScore` 归一化；
- 没有 section 权重；
- 没有 rubric 维度权重；
- 没有区分不同题型；
- `recommendations` 还没有形成稳定生成逻辑；
- 长期能力标签没有从 item result 汇总到学生画像。

这只能算“技术报告骨架”，还不能算产品中的国通语能力报告。

### 断点 5：近期实现没有同步到测试

本次实际验证结果：

```text
pnpm --filter @yuzan/api typecheck
结果：通过

pnpm --filter @yuzan/worker typecheck
结果：通过

pnpm --filter @yuzan/api test
结果：35 个测试文件通过，10 个失败
      705 个测试通过，57 个失败，44 个跳过

pnpm --filter @yuzan/worker test
结果：命令退出 0，但没有测试文件
```

API 失败主要来自：

- service 新增依赖后，旧测试模块没有补 provider；
- Classes、Assignments、Submissions、Learning、Reporting 等测试装配失配；
- PostgreSQL 集成测试使用无效数据库凭据；
- 新测评、录音、SpeechJob、学生/教师聚合和 worker 缺少对应测试。

另外当前 Node 是 `v22.19.0`，项目声明需要 `>=24 <27`。TypeScript 检查虽通过，但不能把 Node 22 作为正式验证环境。

## 四、现在应当正式做出的决定

### 决定 1：产品主线改为“国通语学习—练习—证据—干预循环”

课程和测评不再是两套并列产品。课程提供内容，统一练习引擎提供执行，报告和干预把结果送回下一轮学习。

### 决定 2：P0 只保留一条黄金闭环

第一条闭环选“古诗文朗读与理解训练”，必须同时包含：

- 一个可版本化练习；
- 至少两个口语环节；
- 至少一个书面环节；
- 一套明确评分量表；
- 一次真实录音上传；
- 一次 worker 处理或明确 `PROVIDER_NOT_CONFIGURED`；
- 一次教师复核；
- 一份真实报告；
- 一条后续巩固建议。

### 决定 3：短期保留 `web-runtime`

未来 20 个工作日不做 Nuxt 迁移。只整理当前前端的目录、数据源和状态，优先删除核心链路中的演示 ID、静态业务数据和静默假回退。

### 决定 4：不重复建表重写

短期用现有模型承载：

- `CourseVersion / LearningActivity / Question`：内容来源；
- 新增最小的练习定义、版本、section、rubric 和 delivery；
- `AssessmentSession`：先作为统一 attempt 的底层执行记录；
- `AssessmentItem`：一次 attempt 中的 item；
- `Recording / SpeechJob`：语音证据与自动处理；
- `AssessmentReport / LearningPlan`：报告和干预计划。

等黄金闭环稳定后，再判断是否将 `AssessmentSession` 正式重命名或迁移为 `PracticeAttempt`。

### 决定 5：AI 功能后置

教师备课 Agent、练习生成 Agent 和个性化推荐进入 P1。P0 只允许：

- 人工创建内容；
- 人工配置评分量表；
- 机器产生可审阅的建议；
- 明确标注供应商未配置或结果待复核。

## 六、对这次 AI 对话的最终评价

这次对话最重要的价值，不是它列了多少模块，而是你把产品的真正亮点说清楚了：

> 课程不是内容播放，测评不是一次考试，AI 不是工具卡片；它们必须共同帮助学生持续提高国通语能力，并让教师知道下一步该教什么。

后续与 AI 沟通时，应继续坚持这个产品判断，但每次任务都要补上四项约束：

1. 先说明复用哪些现有模型和接口；
2. 明确本次只打通哪一个用户动作；
3. 写出真实数据来源和失败状态；
4. 写出可执行的验收命令与结果格式。

这样才能把好方向转化成真实产品，而不是再生成一套更完整的概念图。
