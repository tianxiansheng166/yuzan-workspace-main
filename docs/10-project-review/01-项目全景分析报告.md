## 四、项目开发方向是否与项目背景一致？

### 4.1 项目背景核心定位

从 `docs/项目背景/项目想法.md` 提取的核心定位：

1. **面向西藏农牧区学校**的国家通用语言文字学习
2. **两大核心模块**：
   - 前置发音测评模块（发音水平检测 → 薄弱点标注 → 精准课程推送）
   - 课后复测与循环迭代模块（复测 → 前后对比 → 系统化学习建议 → 多轮循环）
3. **核心价值**：AI 赋能的"测评-上课-复测"闭环

### 4.2 方向一致性分析

| 项目背景要求 | 当前实现状态 | 一致性 |
|---|---|---|
| 前置发音测评 | 测评模块全部 NOT_CONFIGURED，无发音打分引擎 | ❌ 不一致 |

| 课后复测 | 无复测对比机制 | ❌ 不一致 |
| 测评-上课-复测闭环 | 闭环三个环节中"测评"缺失 | ❌ 不一致 |
| 西藏农牧区场景 | 藏中翻译系统 12 项问题未修 | ⚠️ 部分一致 |
| 弱网/离线优先 | 离线包 API 已有但前端无入口，PWA 未实现 | ⚠️ 部分一致 |

| 教师复核反馈 | 提交与反馈已对接 | ✅ 一致 |
| 可验证的学习效果 | 成长报告部分对接，但无语音证据 | ⚠️ 部分一致 |

### 4.3 结论

**当前开发方向与项目背景存在显著偏差。**

项目背景的核心差异化是"AI 测评-学习-复测"闭环，但当前开发重心落在了基础 CRUD 和页面框架上，而**最核心的语音评测、测评闭环、智能推荐**这三个能力完全缺失。

简单说：**现在搭了一个通用教学平台的骨架，但产品灵魂（AI 发音测评闭环）还没注入。**

### 5.1 直接对标产品

#### 1. 畅言国通（科大讯飞 iFLYTEK）

- **定位**：面向少数民族地区的国家通用语言学习平台
- **优势**：
  - 教育部认证的口语评测引擎，覆盖听说读写四项
  - 5000万+ 用户量，全国最大国通语学习平台

  - 产品偏"重"，部署周期长，对弱网/离线场景支持有限

## 六、护城河构建建议

### 6.1 语赞心声的差异化定位

在畅言国通（重）、查瓦云（窄）、藏译通（浅）之间，语赞心声的独特位置是：

> **轻量部署 + 离线优先 + 藏中双语 + AI 测评闭环** 的"四合一"组合

没有任何现有产品同时覆盖这四个维度。

### 6.2 具体护城河方向

#### 护城河 1：离线优先的真实教学闭环（最核心）

- **现状**：畅言国通依赖网络，藏区学校网络不稳定
- **差异化**：PWA + IndexedDB + Outbox + 内容包，在完全断网时仍可完成"听课→朗读→录音→同步"
- **实现关键**：必须先把录音上传和离线同步做通，否则这个护城河只是纸上谈兵

#### 护城河 2：藏中双语深度融合

- **现状**：现有产品要么纯中文、要么翻译工具化
- **差异化**：翻译不是独立工具，而是嵌入教学全流程的基础设施——课件双语标注、翻译辅助理解、术语表自动匹配
- **实现关键**：修复 12 项翻译问题、部署 Hunyuan-MT-7B、四端翻译入口上线

#### 护城河 3：AI 发音诊断到课程推荐的自动闭环

- **现状**：畅言国通有评测但推荐偏粗粒度
- **差异化**：音素级发音诊断 → 精确标注薄弱点 → 自动匹配针对性课程 → 复测验证提升 → 循环迭代
- **实现关键**：接入语音评测 Provider（不必自建）、实现测评会话管理、建设"诊断-推荐"算法

#### 护城河 4：低门槛单校部署

- **现状**：畅言国通以区县为单位采购，单校无法独立使用
- **差异化**：单校独立部署、教师自助注册、学生免注册（班级码加入）
- **实现关键**：简化部署流程、做好 onboarding 引导、降低管理端使用门槛

## 七、项目体系与开发流程分析

### 7.1 项目架构

```
yuzan-next/
├── apps/
│   └── api/              # NestJS 11 后端 API
├── frontend/             # 原生 HTML/JS/CSS 前端（4175 端口）
├── packages/
│   ├── contracts/        # OpenAPI 3.1 契约
│   └── database/        # Prisma 7 + PostgreSQL 17
├── infra/                # 基础设施配置
├── docs/                 # 项目文档（本文档所在位置）
├── project-ops/          # 任务管理 JSON + CCR
├── tests/                # 安全测试
└── workers/              # 集成工作区
```

### 7.2 Git 分支与工作流

从 `docs/09-operations/` 可以看出项目采用的是**多 worktree 并行开发 + 集成分支统一合并**的模式：

- **集成分支**：`integration/windows-backend-v31-mvp-20260712`
- **任务分支**：b31-101 到 b31-105，每个任务有独立的 JSON 定义、契约变更请求（CCR）、Schema 变更请求
- **共享文件所有权规则**：Integration Controller 独占 Prisma schema、migrations、OpenAPI、generated contracts、AppModule/main
- **合并规则**：不 squash、不 rebase 共享分支、不 force push、不 reset --hard

### 7.3 断点保存与交接

### 8.2 测试收敛方法

**逐功能通关策略**：每完成一个功能，执行以下 5 步验证：

1. **后端单元测试**：`pnpm --filter @yuzan/api test` — 确保新增代码不破坏现有测试
2. **API 契约测试**：验证接口返回格式与 OpenAPI 3.1 一致
3. **前后端联调冒烟**：手动走通关键路径，确认无 401/404/500
4. **浏览器验收**：在 390/768/1440 三个宽度检查布局、无 console error、无横向溢出
5. **安全验收**：确认租户隔离、权限校验、输入验证

**每个功能通关后打 tag**：`feature/<name>-verified-YYYYMMDD`

### 8.3 避免回归的关键规则

1. **不删旧文件**：移到 `_deprecated/` 文件夹，不 git rm
2. **不 squash 合并**：保留每个任务的提交历史
3. **不改共享文件**：Schema、OpenAPI、AppModule 的变更走 CCR 流程
4. **不返回假成功**：未实现功能必须返回 PERSISTENCE_PENDING，不得返回空数组伪装
5. **每合并一次跑一次全量测试**：typecheck + unit + integration + security
