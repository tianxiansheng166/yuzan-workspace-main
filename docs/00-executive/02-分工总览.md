# 多 AI 与人工角色分工总览

## 必须保留的人类决策

AI 可以实现和审查，但以下决定必须由项目负责人/领域专家确认：

- 面向何种学校与年级；
- 课程内容、藏文翻译和教学评价标准；
- 未成年人数据处理范围；
- 语音反馈是否适合对学生展示；
- 试点学校、商业承诺和比赛数据；
- 视觉中的文化元素是否准确、尊重且不符号化。

## 推荐角色

| 角色                | 主要职责                           | 不得越权                 |
| ------------------- | ---------------------------------- | ------------------------ |
| Product Lead        | 范围、验收、优先级、试点           | 不直接更改契约绕过评审   |
| Integration Lead    | 任务解锁、共享文件、合并、发布     | 不代替领域专家批准内容   |
| Domain/Contract AI  | 领域模型、状态机、OpenAPI          | 不实现整页 UI            |
| API AI              | Nest 模块、权限、数据访问、测试    | 不私自改 OpenAPI/Prisma  |
| Web/Codex AI        | Nuxt UI、交互、视觉资产和浏览器 QA | 不伪造后端数据或接口     |
| Offline AI          | PWA、IndexedDB、outbox、同步       | 不自行定义服务器冲突语义 |
| Speech AI           | 音频链路、适配器、评测与复核界面   | 不承诺未验证准确率       |
| Migration AI        | 旧数据导出、清洗、导入和报告       | 不把旧用户隐私直接迁入   |
| QA/Security AI      | 契约、E2E、权限、安全、性能        | 不只检查 happy path      |
| Docs/Competition AI | 证据、演示、材料一致性             | 不制造数据、论文或合作   |

## 并行原则

- 一个任务一个分支和 worktree。
- 一个任务最多一个主 owner，可有 reviewer。
- OpenAPI、Prisma、token、根配置实行单写者制度。
- 前后端通过 mock server 和生成类型并行，而不是口头约定字段。
- 设计实现通过截图与状态矩阵验收，而不是“看起来不错”。
- 每个功能在合并前必须回答：数据从哪里来、谁能访问、离线怎么办、失败怎么办、如何测试、如何审计。
