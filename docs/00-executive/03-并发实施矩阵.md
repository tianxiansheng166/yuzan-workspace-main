# 并发实施矩阵

## 为什么不能“一人一个页面”

页面分工会产生：

- 四套不同的身份、错误和数据结构；
- 前端先硬编码、后端再追赶；
- 同一状态被不同 AI 命名；
- 合并时大量冲突；
- 看起来页面齐全，业务链仍不通。

因此任务按**纵向业务切片 + 共享基础能力**划分。

## 并发槽位建议

### Wave 0：最多 4–5 个槽位

| 槽位 | 任务 | 共享冲突控制 |
|---|---|---|
| Integration | GOV-001 | 根配置，先合并 |
| Contract | GOV-002 | 唯一 OpenAPI owner |
| Schema | GOV-003 | 唯一 Prisma owner |
| Design | GOV-004 | 唯一 token owner |
| Migration | MIG-001 | 只读 legacy |

GOV-005/GOV-006 在 GOV-001 后加入。

### Wave 1：6–8 个槽位

- IDN-001 身份 API
- IDN-002 身份 Web（基于 mock）
- ORG-001 组织班级 API
- CUR-001 课程 API
- CUR-002 内容工作台（基于 mock）
- WEB-001 应用壳
- CLS-001 班级 Web（基于 mock）
- MIG-001 继续资产审核

集成顺序：Contract/Schema → API → 生成类型 → Web 接真实 API → QA。

### Wave 2：按闭环并行

```text
ASN-001 API ─┐
ASN-002 Web ─┤
LRN-001 API ─┼─→ QA-001 的前置
LRN-002 Web ─┤
QST-001 ─────┤
SUB-001 API ─┤
SUB-002 Web ─┘
```

同时独立推进 OFF-001、DES-001、DES-002。

### Wave 3

- OFF-002 客户端同步与 OFF-003 服务端同步成对推进；
- SPH-001 录音 UX 与 SPH-002 worker 通过契约并行；
- SPH-003 只在真实输出出现后做评测；
- RPT-001 先定义口径，RPT-002 用 mock 设计；
- MIG-002/003 在新内容模型稳定后导入。

### Wave 4

以验证为主，不再大规模扩功能：

- SEC-001
- OPS-001/002
- QA-001/002/003
- CMP-001
- PIL-001

## 每个切片的最小共同接口

每个功能任务需在 issue/PR 声明：

- 输入命令和认证主体；
- 领域状态变化；
- 数据表/约束；
- API 请求/响应/错误；
- 业务事件；
- Web 状态；
- 离线策略；
- 审计；
- 测试和观测。

缺一项时由 reviewer 判断是否为明确“不适用”，不能空白。
