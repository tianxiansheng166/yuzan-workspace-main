# 最终整合决策

## 1. 为什么不能继续修补旧项目

两套诊断和专家意见的共同结论是：当前项目虽有后端、登录、课程和若干 API，但整体仍属于高保真演示原型。问题不是页面数量不够，而是：

- 课程、班级、任务、提交、反馈没有形成稳定领域关系；
- 多数页面存在静态数据、假按钮和重复 HTML；
- JSON 文件承担数据库职责，无法保证事务、并发和租户隔离；
- 全局覆盖 CSS 与运行时 DOM 修补掩盖了结构性问题；
- 安全、审计、备份、离线和未成年人数据治理没有形成体系；
- “微服务”只是示例骨架，继续扩展会放大复杂度。

因此采用“双轨策略”：

1. `legacy/` 保留旧项目、内容和证据，不再承载新生产功能。
2. `yuzan-next/` 重新建立成熟工程，按纵向业务闭环迁移。

## 2. 两套方案如何取舍

另一方案提出“渐进式替换 JSON、Vue 3、Express MVC、Redis”，其中关于安全加固、PostgreSQL、组件化、离线和语音闭环的方向保留；但以下部分升级：

- 不在旧 Express 单文件上继续拆 MVC，而建立新的 NestJS 模块化单体；
- 不以 Element Plus 作为视觉主体，避免通用后台模板感；
- 不先迁移所有旧页面，只迁移首个真实教学闭环；
- 不默认上 Redis，达到队列/热点缓存需求后再启用；
- 不做 JSON 与新数据库长期双写，只做一次性、可复核迁移；
- 不以“三个月完成全部差异化”作为承诺，改为按门禁和试点证据推进。

## 3. 不可变架构决策

- 新旧项目物理隔离。
- 前端：Nuxt 4 + Vue 3 + TypeScript + PWA。
- API：NestJS 11 模块化单体。
- 数据：PostgreSQL + Prisma；对象文件进入对象存储。
- 契约：OpenAPI 3.1 是前后端共享事实源。
- 权限：学校/组织租户隔离 + RBAC + 资源范围校验。
- 异步：独立 worker；队列能力按需启用。
- 离线：内容包、IndexedDB、outbox、幂等写入、冲突策略。
- AI：供应商适配层、预算、审计、可回退、人工复核。
- 设计：自定义 token 与组件，不以第三方 UI 库决定品牌。
- 测试：单元、契约、集成、E2E、安全和视觉回归共同构成完成定义。
- 并发：共享文件单写者；任务按路径白名单领取；集成负责人统一合并。

## 4. 产品定位

> 面向西藏农牧区学校的弱网/离线优先国家通用语言文字教与学平台，以标准化课程、真实任务闭环和可验证的语音学习反馈降低教师备课与干预成本。

## 5. 第一阶段成功标准

- 一套课程能从草稿、审核到不可变发布；
- 一个班级能收到任务；
- 学生可在线/离线完成并恢复同步；
- 教师能依据原始证据复核和反馈；
- 学校报表指标可追溯到业务事件；
- 关键权限和数据隔离有自动化测试；
- 试点至少连续运行四周；
- 技术创新有测量数据，不以宣传语代替证据。
