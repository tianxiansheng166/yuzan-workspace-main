# 领域模型总览

## 边界上下文

1. **Identity & Organization**
   - School, Campus, Term, User, Membership, Role, Class, Enrollment
2. **Curriculum**
   - Course, CourseVersion, Unit, Lesson, LearningActivity, Resource, Review
3. **Teaching**
   - Assignment, AssignmentTarget, AssignmentRevision
4. **Learning**
   - ProgressCheckpoint, ActivityAttempt, Submission, LearningEvent
5. **Assessment & Feedback**
   - Question, Rubric, Grade, Feedback, MasterySnapshot
6. **Offline & Devices**
   - Device, ContentPackage, SyncJob, SyncCursor, SyncOperation, SyncConflict
7. **Speech**
   - AudioAsset, SpeechJob, SpeechResult, SpeechReview
8. **Reporting**
   - MetricDefinition, ReportSnapshot, ExportJob
9. **Governance**
   - AuditLog, ConsentRecord, DataRetentionPolicy

## 聚合边界

- `Course` 聚合只管理草稿和版本创建；发布后的 `CourseVersion` 不可变。
- `Assignment` 固定引用一个 `CourseVersion` 和活动快照，避免内容更新改变历史任务。
- `Submission` 是学生一次任务提交的聚合，内部包含活动作答引用。
- `SpeechJob` 是异步处理聚合，自动结果与教师最终复核分离。
- `SyncJob` 聚合一次 `sync/push` 请求；`SyncOperation` 使用客户端生成的幂等键，必须归属一条 `SyncJob`，服务端保存处理结果。

## 核心不变量

- 一个用户可以属于多个学校，但每次会话必须有明确活动学校。
- 教师只能管理自己在该学期有任课关系的班级。
- 已发布课程版本不可原地改动；内容变更必须创建新版本，并在服务层与测试中校验。
- 已提交答案不可静默覆盖；任何重做生成新 attempt 或 revision。
- 自动评分永远不是教师最终评分的不可见替代。
- 同一个幂等键重复提交必须得到相同业务结果。
- 报表指标必须能追溯到源事件和口径版本。

## Submission 状态语义

- `IN_PROGRESS`：服务端已建立提交记录，作答尚未完成；`submittedAt` 可为空。
- `PENDING_SYNC`：服务端已接收离线提交元数据，仍有内容待同步；`submittedAt` 可为空。
- `SUBMITTED` 及之后状态：`submittedAt` 必须有值。
- `attemptNo` 表示同一 `assignment` 下该 `enrollment` 的整体提交序号，由数据库唯一约束保护。
- 所有持久化到服务端的 `Submission` 都必须有 `idempotencyKey`；`IN_PROGRESS` / `PENDING_SYNC` 是生命周期状态，不代表可无幂等键。

## MVP 实体范围

本次冻结的 Prisma MVP 实体：

- `School`、`Campus`、`User`、`Membership`、`Term`、`Class`、`Enrollment`
- `Course`、`CourseVersion`、`Unit`、`Lesson`、`LearningActivity`
- `Resource`、`ActivityResource`
- `Assignment`、`AssignmentTarget`
- `Submission`、`ActivityAttempt`、`Feedback`
- `Question`、`ActivityProgress`
- `Device`、`ContentPackage`、`SyncJob`、`SyncCursor`、`SyncOperation`
- `AudioAsset`、`SpeechJob`
- `AuditLog`

## 明确暂缓的实体

以下实体已在领域上下文列出，但暂不进入 MVP Schema，由后续任务按需引入：

- `ProgressCheckpoint`、`LearningEvent`：学习过程事件流，MVP 以 `ActivityProgress` + `Submission` 满足核心链路。
- `Rubric`、`Grade`、`MasterySnapshot`：MVP 评分由 `Feedback.score` 覆盖，复杂量规留待教学评估迭代。
- `SpeechResult`、`SpeechReview`：MVP 由 `SpeechJob.result` 承载自动结果，复核记录留待语音服务细化。
- `AssignmentRevision`：任务版本快照由 `Assignment.revision` + 服务层变更日志先行覆盖。
- `SyncConflict`：冲突状态由 `SyncOperation.status = CONFLICT` + 服务层处理覆盖。
- `MetricDefinition`、`ReportSnapshot`、`ExportJob`：报表体系不在 MVP。
- `ConsentRecord`、`DataRetentionPolicy`：未成年人数据最小化原则由字段最小化 + 审计日志先行覆盖，独立合规表留后。

## Campus 在 MVP 中的用途

`Campus` 在本次 MVP 中不是孤立表：

- `Class.campusId`：班级可按校区归属，便于按校区排课与筛选。
- `Device.campusId`：离线设备可按校区下发内容包与统计。

因此 `Campus` 保留在 MVP Schema 中。MVP 不实现按校区的管理权限拆分，留待后续阶段。
