# 语赞心声：项目深度审计与重构路线图

> 审计对象：用户上传的 `two - 副本.zip`  
> 审计日期：2026-07-08  
> 结论定位：当前项目是“高保真演示原型 / 技术样机”，不是可正式投入学校使用的生产级教育平台。

## 1. 执行结论

项目并不是“完全只有前端”，它已经具备 Express 后端、JWT 登录、JSON 数据、课程/进度/资料库/分析等若干 API，也有双语、资源上传和 AI 标注的尝试。但这些能力没有形成稳定的教学业务闭环，页面中大量数据、按钮、图表、导航和业务状态仍然是静态演示或前端兜底。

真正的问题不是页面不够漂亮，而是：

1. 产品范围过大，核心产品没有收敛。
2. 课程、班级、作业、提交、批改、掌握度等核心领域模型缺失。
3. 前端是 16 个超大 HTML 文件，缺乏组件化、路由、状态管理和工程化构建。
4. 后端是单文件同步读写 JSON，存在严重的数据一致性、并发和安全风险。
5. “微服务方案”目前是不可运行的架构样例，不应继续投入。
6. 视觉升级主要依靠全局覆盖 CSS 和 DOM 修补脚本，改善了截图，但没有改善产品本体。

建议停止继续添加页面和视觉特效，先把项目重新定义为：

**面向西藏农牧区学校的、弱网/离线优先的国家通用语言文字教与学平台。**

第一阶段只做完整闭环：

**课程内容 → 教师组课/布置 → 学生学习与练习 → 自动记录 → 教师反馈与干预 → 学校查看成效。**

## 2. 项目现状证据

### 2.1 代码规模

- HTML 页面：16 个
- HTML 总行数：约 13,473 行
- HTML 总体积：约 727 KB
- 按钮：366 个
- 输入控件：86 个
- `href="#"` 等展示型空链接：236 个
- 外部热链图片：43 个
- 内联 `<style>`：27 个
- 内联脚本块：32 个
- 全站覆盖样式中的 `!important`：64 处
- 后端 `server.js`：约 1,256 行
- API 路由：29 个
- 真正直接调用业务 API 的页面：6 个

大量页面在视觉上“像系统”，但并未真正接入业务数据。

### 2.2 前端结构

核心页面均为独立 HTML 文件，例如：

- `index.html`：约 1,730 行
- `course-center.html`：约 1,256 行
- `video-player.html`：约 1,022 行
- `dashboard.html`：约 988 行
- `teacher-dashboard.html`：约 933 行

每个页面重复加载 Tailwind CDN、Font Awesome、Chart.js，并重复声明 Tailwind 主题、侧边栏、卡片、动画等样式。

`public/js/course.js` 在文档中被称为核心课程模块，但没有任何 HTML 页面实际加载它，属于失联代码。

### 2.3 真实后端接入程度

目前有 API 调用的页面主要是：

- `index.html`：登录
- `student-dashboard.html`：部分学习统计
- `student-profile.html`：部分档案数据
- `dashboard.html`：部分分析数据
- `admin-dashboard.html`：部分运营数据
- `platform-internal.html`：课程、资料、上传、AI 标注与搜索

教师仪表板的大部分图表、学生数据、班级数据是硬编码。课程中心没有真正通过 API 加载课程。视频播放器没有完整接入进度保存、任务、练习、笔记和测评闭环。

多个页面采用“先显示完整静态演示数据，再尝试用 API 替换其中几个数字”的方式。这会让页面看起来完整，但业务真实性很低。

## 3. P0：正式上线前必须解决的风险

### 3.1 整个项目根目录被公开托管

`server.js:152`：

```js
app.use(express.static(path.join(__dirname)));
```

这意味着数据库 JSON、源代码、文档、日志、微服务配置等均可能通过 URL 被直接访问。例如 `db/users.json` 包含用户手机号、出生日期、民族、学校、住址、邮箱等信息。

这是当前最严重的问题，应立即改为只公开专门的静态资源目录和构建产物。

### 3.2 内部资料库实际上是公开接口

- `GET /api/materials`：无鉴权
- `POST /api/materials`：无鉴权
- 上传文件通过 `/uploads` 公开访问
- `visibility: internal` 只是数据字段，没有权限约束

因此“内部资料”并不内部。任何调用者都可能读取和上传资料。

### 3.3 AI 接口无身份与额度控制

- `/api/ai/auto-tag`
- `/api/ai/analyze`
- `/api/materials/search`

这些接口可公开消耗第三方 AI 额度，缺少用户级限流、预算、权限、审计、任务队列和内容安全流程。

### 3.4 默认 JWT 密钥

`server.js:13` 使用硬编码开发密钥作为回退。若生产环境未正确配置环境变量，令牌可被伪造。

生产启动时应在缺少密钥时直接失败，而不是回退到默认值。

### 3.5 学习进度存在越权写入

`POST /api/progress` 虽要求登录，却直接信任请求体中的 `userId`，没有验证其与当前用户一致，也没有严格限制教师/管理员的代理写入权限。

### 3.6 JSON 同步读写不适合并发

所有核心数据依赖 `fs.readFileSync` / `fs.writeFileSync`：

- 阻塞 Node.js 事件循环
- 并发更新时可能互相覆盖
- 进程中断可能造成文件损坏
- 无事务、唯一约束、外键和可靠审计
- 无迁移、备份和恢复机制

### 3.7 未成年人数据处理不具备上线基础

当前示例用户包含完整的未成年人资料和学习档案，但项目缺少：

- 隐私政策与监护人同意流程
- 数据最小化
- 敏感字段加密
- 数据访问审计
- 数据导出、删除、更正机制
- 保留期限
- 分级授权
- 脱敏规则
- 内容安全与未成年人模式

## 4. 产品层问题

### 4.1 范围过大，没有第一核心产品

项目同时试图覆盖：

- 课程平台
- 学生学习中心
- 教师工作台
- 学校管理后台
- 志愿者辅导
- 文化社区
- 公益基金
- 商业付费套餐
- 教研资料库
- AI 标注与语义搜索
- 视频学习
- 学情分析

这些模块都做一点，结果是没有一个模块达到真实用户可持续使用的深度。

### 4.2 缺少教学业务的基础实体

当前数据模型缺少或不完整：

- 学校 / 租户
- 校区
- 学年与学期
- 班级
- 班级成员与任课关系
- 课程版本
- 单元
- 课时 / Lesson
- 学习活动
- 题目与题库
- 作业
- 作业发布范围
- 学生提交
- 批改、反馈和重交
- 能力点 / 知识点
- 掌握度
- 内容版本与发布流程
- 课程授权和订阅
- 设备和离线同步状态
- 审计日志

只有“课程 + 进度百分比”无法支撑一个可用的 LMS。

### 4.3 文档目标远大于真实能力

PRD 提到 1,344 课时、AI 语音评测、离线下载、互动练习、作业批改、成长档案、志愿者匹配、社区、基金与支付等，但仓库只有约 10 门样例课程和一个样例视频。

文档还存在明显过期：技术债务文档仍写着“无 JWT、明文密码、无注册”，而当前代码已部分实现。这说明文档没有成为真实的工程契约。

## 5. 前端与视觉问题

### 5.1 视觉升级是覆盖层，不是设计系统迁移

`public/css/yx-design-upgrade.css` 通过全局选择器覆盖：

- `.bg-white`
- `.card`
- `.stat-card`
- `h1/h2/h3`
- 多种按钮和 Tailwind 类

并使用 64 个 `!important`。这会造成：

- 原组件含义被全局改变
- 页面局部修改容易产生连锁反应
- 难以识别最终样式来源
- 新旧设计体系长期共存
- 测试和维护成本持续上升

### 5.2 `site-polish.js` 在修补页面结构

该脚本会：

- 动态注入升级 CSS
- 给 body 添加页面类别
- 扫描所有 `href="#"` 并根据可见文字猜测路由
- 动态插入教研资源库入口
- 覆盖 `window.alert`
- 给失败图片换成任意备选图
- 插入首页文案

这类“运行时美化与补洞”让演示变得完整，却把结构问题隐藏起来。正式重构后应删除大部分逻辑。

### 5.3 外部图片不可控

大量页面热链带签名和过期参数的豆包/字节图片链接：

- 链接可能失效
- 来源授权不清晰
- 生产环境受第三方可用性影响
- 弱网访问体验差
- 无统一裁切与压缩策略

### 5.4 页面仍是后台模板结构

视觉资产有一定特色，但学生、教师和管理员端仍然是：

- 左侧菜单
- 四张等宽统计卡
- 多个白色面板
- Chart.js 图表
- 大量 Font Awesome 通用图标

这不是最严重的问题。真正需要先改的是信息架构和任务流，之后才重新做视觉表达。

## 6. “微服务”目录的判断

`microservices/` 目前不是可用架构，而是文档性样例：

- 文档声明 6 个业务服务，实际只有 user-service 和 course-service
- 多个服务在 compose 中被注释
- API 网关只用 GET 转发，无法正确代理登录 POST、请求体、请求头和其他方法
- Redis v4 客户端没有建立连接，且使用旧式 API
- PostgreSQL 初始化脚本把数据库名当作 schema 使用，初始化逻辑不可直接成立
- Prometheus 配置抓取 `/metrics`，但服务没有暴露指标
- 配置引用不存在的 Alertmanager、Grafana dashboard 目录和未实现服务
- Docker 配置含默认密码与固定密钥

当前阶段不应做微服务。正确选择是“模块化单体”。

## 7. 建议的产品重新定位

### 7.1 核心用户

- 购买与决策者：学校 / 教育管理者
- 高频操作用户：一线教师
- 最终学习用户：学生
- 内容生产者：教研员 / 认证教师

志愿者、公益基金和文化社区暂时作为后续扩展，不进入第一版核心闭环。

### 7.2 核心价值

不是“又一个教育资源网站”，而是：

1. 适配本地文化和国家通用语言教学的结构化课程。
2. 教师能低门槛布置、使用和调整课程。
3. 学生在弱网或局域网下仍能完成学习和练习。
4. 教师能看到真实掌握情况，而不只是播放进度。
5. 学校能看到使用率、完成率、能力变化和资源覆盖情况。

### 7.3 第一版闭环

1. 教研员发布课程版本。
2. 教师选择课程内容，组成班级任务。
3. 学生收到清晰的今日任务。
4. 学生观看、阅读、听说和答题。
5. 系统保存提交与掌握度。
6. 教师查看谁完成、谁卡住、错在哪里。
7. 教师给出反馈或追加练习。
8. 离线设备恢复连接后同步数据。
9. 学校查看班级与学期成效。

## 8. 对标产品与学习重点

### Kolibri

最值得深入研究。它不是因为界面最漂亮，而是因为真正围绕“无互联网也能教学”设计：本地设施、内容频道、学习设备、教师/教练、班级、课程、测验、进度和设备同步。

应学习：

- 离线内容包和版本
- 校内服务器 / 局域网模式
- 学习设备与中心节点同步
- 教师看到设备最后同步时间
- Lesson / Quiz / Class / Group 的模型

### 国家中小学智慧教育平台

应学习：

- 资源分类体系
- 学段、年级、学科、教材、章节等多层导航
- 公共资源与教师研修的分区
- 权威内容的元数据和检索方式

不要照搬门户式视觉密度。

### 希沃 / ClassIn

应学习：

- 教师课前、课中、课后的连续工作流
- 资源、班级、作业、学情不是分散页面，而是相互连接
- 管理端围绕班级、人员、课程和教学质量组织
- 学习报告直接服务教师行动

不要在第一版复制复杂直播课堂、硬件和实时互动体系。

### Moodle / Canvas

应学习成熟 LMS 的领域骨架：

- 课程与选课
- 角色、权限和上下文
- 作业、测验、成绩册
- 分组
- 审计
- 可扩展集成

不要照搬通用 LMS 的复杂菜单和企业后台视觉。

### Khan Academy / Duolingo for Schools

应学习：

- 学生首页只强调“下一步做什么”
- 任务拆解为可完成的小步骤
- 进度必须可理解、可行动
- 教师能看学习时长、任务和掌握情况
- 激励服务于持续学习，而不是堆徽章和排行榜

## 9. 推荐目标架构

### 9.1 架构原则

- 模块化单体优先
- 真实业务模型优先
- API 契约优先
- 数据库约束优先
- 离线同步作为独立能力设计
- AI 作为辅助功能，不成为核心数据层
- 不追求微服务数量

### 9.2 建议工程结构

```text
apps/
  web/                 # Next.js 或 Nuxt，公共官网 + 登录后应用
  api/                 # NestJS / TypeScript 模块化 API
packages/
  ui/                  # 品牌设计系统与无障碍组件
  contracts/           # API 类型、Schema、错误码
  config/              # lint、tsconfig、测试配置
infra/
  docker/
  migrations/
  monitoring/
```

### 9.3 基础设施

- PostgreSQL：核心业务数据
- 对象存储：视频、封面、教案、附件
- Redis：只在真正需要队列、缓存、限流时引入
- 后台任务：转码、内容分析、AI 标注、报表
- CDN：联网场景的静态资源分发
- PWA / 本地数据库：设备缓存和同步队列

### 9.4 后端模块

- Identity：登录、会话、密码、设备
- Tenant：学校、校区、学年、组织
- Membership：角色、班级成员、任课关系
- Curriculum：课程、单元、课时、知识点
- Content：资源、版本、发布、审核
- Assignment：作业、范围、截止时间
- Submission：答案、附件、批改、反馈
- Learning：活动日志、进度、掌握度
- Offline Sync：设备、内容包、增量同步、冲突
- Analytics：班级、学校和课程指标
- Audit：敏感操作与数据访问日志

### 9.5 身份和权限

- 使用 HttpOnly Secure Cookie 或可靠的 Token 刷新机制
- 多学校租户隔离
- RBAC + 资源所有权检查
- 每个接口在服务端验证权限
- 内部资源不依赖前端隐藏
- 未成年人敏感字段单独加密和授权

## 10. 分阶段重构路线

- 登录、角色、租户隔离

### 阶段 2：教学闭环 MVP（7–12 周）

### 阶段 4：教研与试点（17–20 周）

- 内容版本和审核

### 延后功能

- 在线社区
- 公开作品墙
- 志愿者智能匹配
- 商业支付和公益基金账务

## 11. 视觉重构策略

视觉方向“高原声纹地图”可以保留，但不能继续作为补丁覆盖在旧页面上。

建议：

1. 公共官网可以更艺术化，承担品牌表达。
2. 学生端强调下一步任务、学习节奏和成就感。
3. 教师端强调班级、任务、需要帮助的学生和下一步行动。
4. 管理端强调覆盖、活跃、完成、掌握和风险。
5. 教研端强调内容版本、审核和复用。
6. 不同角色共享设计语言，但不共享同一个“统计卡 + 图表”模板。
7. 只保留少量品牌纹理；核心操作界面优先清晰、快速和弱网可用。

重构后应删除：

- 运行时猜测链接的逻辑
- 运行时注入导航入口
- 全局覆盖所有 `.bg-white`、标题和卡片的规则
- 随机图片 fallback
- 大部分 `!important`
- 第三方热链图片

## 12. 团队与时间的现实预期

在需求已收敛、课程内容已有基本来源的前提下，一个小型团队完成“可在少量学校试点的版本”，通常至少需要：

- 1 名产品/项目负责人
- 1 名教育业务或教研负责人
- 1 名产品设计师
- 2 名全栈或前后端工程师
- 1 名测试（可阶段性投入）

建议预留约 4–6 个月完成可控试点，随后根据真实教学反馈继续迭代。若要求多校商业化、完整离线同步、语音评测、支付和大规模运营，周期应按更长期产品建设考虑，而不是依赖一次 AI 自动生成。

---

## 13. 下一步最合适的行动

下一步不要直接让 Codex“重构全项目”。应先完成两个交付物：

1. **产品范围与领域模型文档**：明确第一版角色、核心流程、实体、状态和验收。
2. **新架构骨架**：建立可测试的新工程，只迁移登录、学校/班级、课程/课时和任务闭环。

旧项目保留为视觉和需求参考，不在原有 16 个 HTML 页面上继续无限修补。采用“绞杀者迁移”方式：新系统完成一个闭环，就逐步替换旧页面。
