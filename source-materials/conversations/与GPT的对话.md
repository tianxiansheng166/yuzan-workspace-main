# 一、我在项目里发现了什么

## 1. 页面很多，但真实业务接入很少

项目中有：

- 366 个按钮
- 86 个输入控件
- 236 个 `href="#"` 类空链接
- 43 张外部热链图片
- 27 个内联样式块
- 32 个内联脚本块

但真正直接调用业务 API 的页面主要只有：

- 首页登录
- 学生学习中心
- 学生档案
- 部分数据看板
- 管理员看板
- 教研资源库

- `course-center.html` 看起来是完整课程中心，却没有真正从 `/api/courses` 加载课程。

这就是典型的 AI 原型现象：

> 页面先做得像完整产品，再用少量 API 替换几个数字，让系统看起来已经能工作。

## 2. 前端不是一个真正的前端应用

目前主要是多个巨大的 HTML 文件：

- `index.html` 约 1,730 行
- `course-center.html` 约 1,256 行
- `video-player.html` 约 1,022 行
- `dashboard.html` 约 988 行
- `teacher-dashboard.html` 约 933 行

- Tailwind CDN
- Font Awesome
- Chart.js
- Tailwind 配置
- 导航样式
- 卡片样式
- 动画和响应式规则

这会造成：

- 修改一个按钮，要在很多页面重复修改
- 页面之间逐渐不一致
- 无法可靠测试
- 无法进行组件级维护
- CSS 选择器互相覆盖
- AI 每次修改都可能再增加一层补丁

## 3. 现有“视觉升级”本质上仍然是覆盖补丁

你之前提到的两个文件确实存在：

```
public/css/yx-design-upgrade.css
public/js/site-polish.js

```

其中：

- `yx-design-upgrade.css` 有约 64 处 `!important`
- 它会全局覆盖 `.bg-white`、`.card`、标题、按钮等通用类
- 很多旧页面结构并没有改变，只是被新的背景、圆角和纹理包裹

`site-polish.js` 更值得警惕，它会：

- 动态插入样式
- 根据页面文字猜测链接去向
- 修改 `href="#"`
- 注入资源库入口
- 替换 `window.alert`
- 图片失败时自动换成兜底图片
- 动态补充页面文案和类名

这类脚本适合做短期演示，不适合生产系统。

因为页面结构稍微变化，它就可能失效；页面加载时还可能出现闪烁、跳动和语义错误。

所以现在虽然截图比最初漂亮，但底层依旧是：

> 旧模板页面 + 全局 CSS 覆盖 + DOM 修补脚本。

# 二、目前存在非常严重的安全问题

这些问题比视觉问题更优先。

## 1. 整个项目根目录可能被公开访问

`server.js` 中存在：

```
app.use(express.static(path.join(__dirname)));

```

这意味着服务器可能直接对外暴露整个项目目录，而不只是 `public`。

其中包括：

```
db/users.json
设计文档
服务端源码
配置文件
其他数据文件

```

而 `db/users.json` 中包含了姓名、电话、出生信息、学校、地址、邮箱等真实结构的个人信息。

这是必须立即修复的 P0 问题。

***

## 2. JWT 使用了默认开发密钥

代码中存在默认值：

```
'yuzan-xinsheng-dev-secret-2026'

```

一旦生产环境没有正确配置环境变量，攻击者可能伪造登录令牌。

***

## 3. 上传和 AI 接口缺乏有效保护

资源上传、自动标签、AI 分析和部分搜索接口没有完整的身份、角色、额度和所有权校验。

结果可能包括：

- 未登录上传文件
- 滥用 AI 接口消耗付费额度
- 上传恶意文件
- 获取不应公开的内部资源
- 污染资源库数据

***

## 4. 学习进度存在越权风险

`POST /api/progress` 接受请求正文中的 `userId`。

这意味着登录用户可能通过修改请求参数，为其他用户写入或篡改学习进度。正确做法应从经过验证的登录身份中取得用户 ID，并检查课程、班级和任务关系。

***

## 5. JSON 文件不能作为正式数据库

目前核心数据依靠同步读写 JSON 文件：

```
db/users.json
db/courses.json
db/progress.json
db/materials.json

```

在多用户同时使用时可能出现：

- 请求阻塞
- 数据覆盖
- 文件损坏
- 并发写入冲突
- 没有事务
- 没有可靠查询
- 没有备份和迁移体系

它适合演示，不适合学校正式使用。

# 三、不要先“把现有项目继续补完整”

我不建议沿着当前结构继续加页面、加接口、加视觉特效。

继续补下去，很容易变成：

- 30 个超大 HTML 页面
- 一个 3,000 行的 `server.js`
- 十几个 JSON 数据文件
- 更多覆盖 CSS
- 更多 DOM 修补脚本

更合理的方法是：

不是全部推倒重来，也不是继续在旧地基上盖楼。

# 六、建议的生产架构

不建议采用项目中现有的“微服务示例”。

目前 `microservices` 目录存在许多演示性问题：

- 文档宣称有多个服务，实际只有少量骨架
- 网关主要代理 GET 请求
- POST 请求、请求体和认证转发并不完整
- Redis 客户端使用方式有问题
- PostgreSQL 初始化脚本混淆数据库和 schema
- Prometheus 试图抓取不存在的 `/metrics`
- 引用了缺失的服务和监控配置
- 密码和密钥被硬编码

这不是可部署的微服务架构，而是架构概念演示。

## 更适合你当前阶段的是模块化单体

一种可行结构是：

```
apps/
  web/                 前端应用
  api/                 后端 API

packages/
  ui/                  设计系统和公共组件
  contracts/           API 类型、校验规则
  shared/              公共工具和领域类型

infra/
  docker/
  database/
  deployment/

```

### 技术选择示例

```
前端：Next.js / Nuxt
后端：NestJS + TypeScript
数据库：PostgreSQL
文件：对象存储
缓存/队列：按需使用 Redis
离线：PWA + 本地数据库 + 同步队列
测试：单元测试 + API 集成测试 + Playwright

```

关键不是一定采用这些框架，而是：

- 一个明确的前端应用
- 一个模块化后端
- 一个正式关系型数据库
- 明确的数据模型
- 明确权限边界
- 可自动测试和部署

# 九、视觉重构应该放在什么位置

“高原声纹地图”可以保留，但需要从装饰主题转化为产品设计系统。

建议只保留两个核心视觉母题：

- 主母题：学习路径与地形线
- 辅助母题：语言与声波

然后应用到：

- 学习进度路径
- 音频练习反馈
- 课程分类
- 离线内容包状态
- 教师干预提示
- 品牌封面和课程封面

不要每页都使用：

- 经幡
- 印章
- 纸张纹理
- 等高线
- 声波
- 山脉
- 暖色渐变

否则会从 AI SaaS 模板变成“文化元素主题模板”。

优秀设计必须首先服务于任务：

- 学生下一步做什么
- 教师今天需要关注谁
- 内容是否已经下载
- 数据是否已经同步
- 任务是否完成
- 学习困难在哪里

# 十、涉及未成年人数据，不能后补合规

这个项目会处理学生身份、学习记录、班级、学校、行为日志，甚至可能涉及民族、地址、联系方式等敏感字段。

正式投入使用前，至少要建立：

- 数据最小化
- 监护人或学校授权机制
- 敏感数据加密
- 分级权限
- 操作审计
- 数据保留和删除规则
- 导出和纠错流程
- 上传内容安全检查
- 安全事件响应

中国现行的未成年人网络保护和网络数据管理规则已经对未成年人信息、个人信息处理和平台责任提出明确要求。这里应当在产品和架构阶段处理，而不是上线前临时补隐私政策。([国家市场监督管理总局](https://www.cac.gov.cn/2023-10/24/c_1699806932316206.htm?utm_source=chatgpt.com "未成年人网络保护条例"))
