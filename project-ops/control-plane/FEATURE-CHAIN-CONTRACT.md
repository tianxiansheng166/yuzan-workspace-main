# 功能链合同：页面不是完成单位

## 为什么

一个页面可以渲染几十个按钮、卡片和板块，但仍然没有一个用户结果成立。静态扫描只能证明
控件存在、脚本可能绑定、页面可能引用 API；它不能证明点击成功、持久化或另一个角色看得见。

因此开发和验收的最小单位是 `FeatureChain`：

```text
角色 + 页面 + 控件
→ 用户点击/输入
→ 前端 handler
→ 真实 API
→ 领域对象与状态转换
→ 数据库/对象存储
→ 当前页面反馈
→ 下游角色/页面观察
→ 刷新、新会话和越权负向
```

## 状态

| 状态 | 含义 | 能否称为功能 |
| --- | --- | --- |
| `DISCOVERED` | 静态源码发现控件 | 否 |
| `DEAD_CONTROL` | 可见可点但没有可识别动作或动作失败 | 否 |
| `UI_ONLY` | 有本地交互/导航，无真实服务结果 | 否 |
| `HANDLER_PRESENT` | 找到事件绑定，尚未证明真实 API | 否 |
| `API_BOUND` | 页面真实发起契约请求 | 否 |
| `PERSISTED` | 动态对象在数据层可追溯，刷新保留 | 部分 |
| `CROSS_ROLE_VERIFIED` | 下游角色新会话可见且权限负向成立 | 是 |
| `REMOVED` | 经产品决定删除无价值控件 | 是，作为清理结果 |

静态扫描不得把控件标记超过 `HANDLER_PRESENT` 或页面级 `API_REFERENCE_PRESENT`。

## 必填字段

每个功能开发任务开始前要冻结：

- `feature_chain_id`、Goal revision、acceptance item；
- actor、route、control selector、可见文案；
- 用户点击后页面应出现的精确结果；
- 请求 method/path 和错误状态；
- 创建/修改的领域对象、关键字段和状态转换；
- 哪个下游角色在什么页面观察到结果；
- 刷新/重新登录行为；
- 越权、重复点击、弱网或 provider 不可用中的至少一个负向路径；
- 完成所需 L3/L4/L5 journey。

缺少后端能力时，任务不能只“先把前端做好”。允许先定义控件和真实 unavailable 状态，但同一
FeatureChain 必须生成后端/契约子任务并保持整体未完成。Controller 按依赖派发，不能让前端
任务关闭整条功能链。

## 盘点流程

1. 运行静态扫描，发现页面、控件、潜在事件绑定、页面级 API 引用和硬编码风险；
2. 在运行环境使用 Playwright 侦察真实可见/可用控件和页面错误；
3. 产品负责人对每个业务控件决定 `实现 / 删除 / 延后`；
4. 对“实现”的控件创建 FeatureChain，补齐前端、契约、后端、数据和下游观察；
5. 任务只推进一个或一组共享同一对象状态的 FeatureChain；
6. Verifier 通过真实点击和动态 ID 将状态推进到 `CROSS_ROLE_VERIFIED`。

## 防止重复与耦合失控

- 同一个领域动作只允许一个规范 API/服务，不为第二个页面复制逻辑；
- 多页面复用通过统一 DTO、状态枚举和组件/客户端方法；
- Controller 以 `domain_action + object + state_transition` 计算幂等键，重复 FeatureChain 合并；
- 前端要用的数据必须能指出来源对象和权限范围；没有消费者的数据字段不为“以后可能用”加入 P0；
- 卡片展示值、列表数量和进度都必须有数据口径，未接数据时显示明确 unavailable/empty，不写固定数。
